# SLSA — Supply-chain Levels for Software Artifacts

[SLSA v1.0](https://slsa.dev/spec/v1.0/) defines four levels of build-process integrity guarantees: **L0 (no guarantees) → L1 → L2 → L3**. Each level adds stronger attestation about how a release artifact was produced and how easy it is to reproduce.

## Target and status

| Level | Target | Current status |
|---|---|---|
| **L1** — provenance exists | **met at v1.0.1** | build runs on GitHub Actions (hosted); CycloneDX SBOM generated per release via Anchore Syft |
| **L2** — signed provenance | **post-1.0.x** | requires a signed release workflow — roadmap below |
| **L3** — hardened build | not planned for single-maintainer | requires reviewers independent from maintainer |

## L1 — what SKIFF does today

- **Source**: public git repo on GitHub.
- **Build**: all release artefacts produced by the pinned GitHub Actions workflow in [`.github/workflows/`](../../.github/workflows/). Build scripts are in the repo; no out-of-band steps.
- **Provenance**: [CycloneDX SBOM](https://cyclonedx.org/) generated by `anchore/sbom-action` on every PR and uploaded as a 30-day retention artifact. Every runtime dependency + transitive is enumerated with its exact version.
- **Isolation**: each workflow job runs on a fresh GitHub-hosted `ubuntu-latest` runner. No self-hosted runners.

That is the full SLSA L1 checklist.

## L2 — what's missing (tracked gap)

L2 adds: **provenance must be signed by the build platform**, and **provenance must be unforgeable by the project owner**. The missing pieces at v1.0.1:

1. **Release workflow**. SKIFF does not currently have `.github/workflows/release.yml`. Releases today are cut manually via `git tag + gh release create`. The artefacts are produced, but no SLSA provenance attestation accompanies them.
2. **Signed tags**. The `v1.0.0` git tag is unsigned. v1.0.1 onward should be signed (GPG or Sigstore) so downstream consumers can verify tag integrity.
3. **Attestations published with the release**. [`slsa-github-generator`](https://github.com/slsa-framework/slsa-github-generator) provides a drop-in GitHub Action that emits SLSA L3-style provenance attestations for a release. SKIFF doesn't yet wire it in.

Roadmap to close the gap:

```yaml
# .github/workflows/release.yml (planned)
on:
  push:
    tags: ["v*.*.*"]

jobs:
  build:
    # Build the Python source + wheel distribution
  provenance:
    uses: slsa-framework/slsa-github-generator/.github/workflows/generator_generic_slsa3.yml@<SHA>
    with:
      base64-subjects: ${{ needs.build.outputs.hashes }}
  release:
    # Attach the dist + the signed .intoto.jsonl provenance to the GitHub release
```

Blocked on maintainer decision about tag-signing key management (GPG vs Sigstore keyless) — not a code problem.

## L3 — not a planned target

L3 requires that the build platform enforces that no single person can forge provenance, which in practice means "at least two maintainers with separate signing keys review each release". A single-maintainer OSS project by design cannot meet this.

An organisation forking SKIFF into their own SDLC CAN meet L3 by adding their own second-pair-of-eyes review step — SKIFF's artefacts don't prevent that, they just can't claim it upstream.

## Verifying a SKIFF release (L1)

Until the signed-release workflow lands, manual verification for a given tag:

```bash
TAG=v1.0.0  # the tag you want to verify
git fetch --tags
git tag -v "$TAG" 2>/dev/null  # pre-L2 this returns "no signature"; that's expected today

# SBOM for the tag's release
gh release download "$TAG" -p 'sbom.cdx.json'
# Confirm every dep in requirements.txt is in the SBOM
pip install cyclonedx-bom pip-licenses
python -m cyclonedx_py environment --requirements requirements.txt --format json | \
    diff - sbom.cdx.json  # should be a subset relationship
```

After L2 lands, `gh attestation verify` will do this in one step.
