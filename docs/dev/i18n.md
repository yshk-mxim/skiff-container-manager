# Localisation posture

SKIFF ships English-only today. The infrastructure to add a second
language is in place; the translation workflow is not. This note
explains what is and isn't wired so a future contributor (or a future
maintainer) can reason about the step-size before spending days on it.

## What's in place

- **One strings bundle.** Every user-facing UI string used by the
  already-migrated pages lives in
  [`skiff/static/strings.en.js`](../../skiff/static/strings.en.js) as a
  nested dict on `window.SKIFF_STRINGS`.
- **One lookup helper.** `ui.js` defines `t(key, vars?)`. Dotted keys
  walk the dict; missing keys return the key itself (so misses render
  visibly instead of silently becoming an empty string). `{placeholder}`
  substitution happens at the call site.
- **Volumes page converted as an exemplar.**
  [`skiff/static/pages/volumes.js`](../../skiff/static/pages/volumes.js)
  is the migrated reference. Every inline English literal in that file
  now goes through `t(...)`.
- **Server-side error envelope.** Every 4xx / 5xx response uses the
  documented `{detail: {code, message}}` shape. The `code` is the
  stable machine-readable identity (catalogued in
  [`docs/errors.md`](../errors.md)); `message` is a short English
  human string. When a future commit adds a second-language UI, the
  client looks up its own translation keyed on `code` and ignores the
  server-supplied English `message`.

## What's NOT in place

- No runtime language picker. Only `strings.en.js` loads.
- No `strings.<lang>.js` bundles.
- No translation workflow. A new UI string lands in `strings.en.js`
  with no obligation to translate it.
- No RTL support. Several CSS rules in `styles.css` use directional
  properties (`margin-left`, `padding-right`, `float: left`). An
  Arabic/Hebrew adopter will need a `dir="rtl"` + logical-property
  pass.
- No pluralisation helper. `{count} volumes` reads fine in English
  whether count is 0, 1, or 100; Russian, Arabic, and Polish need
  `Intl.PluralRules`. Add it with the picker.
- No `Intl.DateTimeFormat` wrapper. Call sites use
  `Date.prototype.toLocaleString()` directly, which picks up the
  browser's locale without any SKIFF code; fine until a deployment
  wants a forced locale independent of browser.
- Incomplete coverage. Only the volumes page and the top-level nav are
  fully migrated. Other pages (containers, images, networks, compose,
  system, wizard) still have inline English literals. That's
  deliberate: converting one page proved the pattern; migrating the
  rest is post-1.0 work a contributor can do incrementally.

## When someone asks for a translation

The right sequence is:

1. Open an issue on the repo confirming the language + who will own
   translations ongoing. The maintainer can't review translations for
   languages the maintainer doesn't read, so a community owner is the
   gating factor — not the code.
2. Copy `strings.en.js` to `strings.<iso-code>.js`, translate values,
   leave structure identical.
3. Wire a picker: read from an `Accept-Language`-aware cookie or
   `localStorage.skiff_lang`, swap the `<script>` tag's `src` at boot.
4. Add a CI test asserting every key present in `strings.en.js` is also
   present in every sibling bundle (rot check).
5. Add `Intl.PluralRules` + `Intl.DateTimeFormat` wrappers in `ui.js`
   if any string in the new bundle needs pluralisation.

Rough effort estimate (excluding the translation work itself):

- Steps 1, 3, 4, 5 above: ~1–2 days of coding.
- Full migration of remaining pages onto `t(...)`: ~2–3 days.
- Per-language translation work (currently ~170 string leaves in
  `strings.en.js`; full UI migration will grow this to ~250–300):
  ~4–8 hours per language if a native speaker owns it; substantially
  longer if community-sourced without a domain-fluent reviewer.

## When someone asks for i18n *pre*-1.0

Translation is a community-owned effort and SKIFF won't stockpile
translated strings waiting on a hypothetical contributor. The
single-maintainer cost model makes every new user-facing string in
every future PR a multi-language coordination problem; the maintainer
can't review translations into languages they don't read. If you'd
like a particular language supported, please open an issue naming the
language AND who will own translations going forward — that pair is
the gating factor, not the code.

## Adding a string (today)

1. Put it in `skiff/static/strings.en.js` under the narrowest namespace
   that fits.
2. Use `t("<dotted.key>")` at the call site. No `UI.t(...)` needed —
   `t` is exposed as a bare global.
3. For placeholders, use `{name}` in the value and pass a dict:
   `t("containers.confirm.remove", { name: container.name })`.
4. If the string is a button label, use the `common.*` tier first
   (cancel/close/copy/delete); subclass only when the verb genuinely
   differs.
5. Add the new key to `_REQUIRED_KEYS` in
   [`tests/test_strings_bundle.py`](../../tests/test_strings_bundle.py)
   only if a page actively depends on it — the test's job is to catch
   accidental deletion, not to track every string.

Do NOT reach for translation infrastructure on individual PRs. The
pre-i18n posture is: ship in English, put the string in the bundle,
let a future contributor translate in bulk.
